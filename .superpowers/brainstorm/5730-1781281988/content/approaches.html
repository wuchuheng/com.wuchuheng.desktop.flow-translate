Architecture Approaches

Three ways to structure the history feature within the existing codebase.

A

Hybrid (Recommended)

Main process: HistoryService + IPC handlers for CRUD + file I/O

Renderer: useHistory hook + extend useShortcuts

Follows exact existing pattern (like useTranslation + translation IPC)

Adds: History entity, history IPC module, useHistory hook

B

Main-process heavy

All navigation state + caching logic in main process

Renderer is a "dumb" display — just renders what main sends

More IPC chatter, goes against existing renderer-state pattern

C

Renderer-only

History state entirely in React, JSON files read/written via preload

No new DB entities, no main-process service

Simpler but breaks existing data-access patterns

Why Approach A fits best

Pros

  • Matches existing architecture: IPC auto-registration, TypeORM entities, React hooks
  • Main process owns data (DB + files), renderer owns UI state
  • Same pattern as useTranslation / translation IPC
  • Adds ~4 new files, extends ~3 existing files

Trade-offs

  • More files than approach C
  • IPC latency for each history operation (negligible for local SQLite)
